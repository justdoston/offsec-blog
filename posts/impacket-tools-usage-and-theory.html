Before copying commands, understand what Impacket actually does

Most of us meet Impacket when we see a command like impacket-psexec in a walkthrough. We put credentials into it, press Enter, and a shell appears. But how did it appear? Did SMB execute our command? Why did one account work while another account could only list shares? Let's focus on the process behind the command first.

Impacket is a Python collection for working with network protocols. Its example programs use those protocols to talk to Windows, Active Directory, databases, and other services. Some query information, some perform administrative operations, some work on local evidence files, and some demonstrate particular vulnerabilities. The name of the tool does not tell us which permission check the server will apply.

This post covers all 68 standalone Python examples in the Kali package snapshot python3-impacket 0.13.0+git20251120-9c2d8b6-0kali1, reviewed on September 20, 2026. Kali is rolling, so another installation can have additional scripts or different options. We will explain useful command combinations and the major operating modes of every tool in this inventory; this is not a claim that every possible permutation of flags behaves the same on every Windows version.

Examples use an imaginary assessment lab: lab.example, domain controller dc01.lab.example at 192.0.2.10, member server srv01.lab.example at 192.0.2.20, and Kali at 192.0.2.50. alice is an ordinary domain user; labadmin has the specific administrative rights discussed in each example. Replace these names with your authorized lab. Commands below explain behavior; they are not a claim that every scenario was executed against a Windows lab.

Kali command names and version differences

dpkg-query -W python3-impacket impacket-scripts
command -v impacket-psexec
impacket-psexec -h
python3 /usr/share/doc/python3-impacket/examples/CheckLDAPStatus.py -h

The first command shows package versions. The second locates a launcher. Kali launchers normally start the corresponding script under /usr/share/doc/python3-impacket/examples/. A script can exist there without an impacket- launcher, so the last command shows the direct Python form. In this post the seven scripts without a launcher in the checked installation use that form. A locally installed Python library can also override the packaged library: a different version banner is a reason to check the Python environment before assuming an option or import is broken.

Most tools use -h; karmaSMB and mqtt_check support --help. The old ping, ping6, sniff, sniffer, and split examples use positional arguments instead of the same help parser. Do not assume that passing -h to every old example is harmless help discovery.

Authentication and authorization are two different checks

Authentication: who are you? A password, NT hash, or Kerberos ticket can establish an identity. Authorization: what may this identity do? Reading a share, writing a file, creating a service, reading a LAPS password, and replicating directory secrets are separate permissions. Valid credentials answer the first question. They do not answer all the others.

SMB normally uses TCP 445 for shares and named pipes. LDAP commonly uses TCP 389, or 636 with TLS, to query directory objects. Kerberos uses the KDC on port 88; these examples commonly use TCP. RPC can travel inside SMB named pipes, or use TCP 135 to locate an interface on another negotiated TCP port. WMI and DCOM often need those additional RPC ports. SQL Server commonly listens on TCP 1433, but an instance can use another port. An open port proves reachability, not permission.

Read the target string carefully

impacket-smbclient 'lab.example/alice@srv01.lab.example'
impacket-GetADUsers 'lab.example/alice' -dc-ip 192.0.2.10 -all

In the SMB example, the part before @ is the identity and the part after it is the server. The LDAP example takes a domain identity, with the DC selected separately. Omitting a plaintext password normally causes a prompt. Single quotes protect characters such as $ in machine account names from the Linux shell. A local account belongs to the target computer, while a domain account belongs to AD; a similarly named local and domain user are not the same identity.

Password, NT hash, AES key, or ticket?

impacket-smbclient 'lab.example/alice@srv01.lab.example' -hashes ':<ALICE_NT_HASH>'
impacket-getTGT 'lab.example/alice' -aesKey '<ALICE_AES_KEY>' -dc-ip 192.0.2.10
export KRB5CCNAME="$PWD/alice.ccache"
impacket-smbclient -k -no-pass 'lab.example/alice@srv01.lab.example' -dc-ip 192.0.2.10

Angle-bracket values are placeholders, not literal keys. -hashes uses the format LMHASH:NTHASH; an empty LM half is commonly written as a leading colon. In an NTLM exchange, the NT hash can supply the secret used to calculate the challenge response. A captured NetNTLMv2 response is different: it is tied to a challenge and cannot simply be pasted here as an NT hash.

An AES key is Kerberos key material. getTGT uses it to request a ticket from the KDC; it does not recover the account's password. KRB5CCNAME selects a credential cache. -k asks a compatible tool to use Kerberos, and -no-pass suppresses a password prompt. They do not create a ticket or grant additional rights. A cache must contain usable credentials, and some tools can fall back to supplied key material when the cache is insufficient.

Kerberos normally needs the service's hostname and SPN, not just its IP address. Where available, -target-ip changes the network destination while preserving the hostname used for authentication. -dc-ip identifies the KDC; it is not a substitute for the target service. DNS, time synchronization, SPN registration, and permitted encryption types all matter. The NT hash is also the RC4 Kerberos key, but it is not an AES key, and an AES-only environment will not accept an RC4-only workflow.

Do not transfer flags blindly between tools. For example, getPac does not expose the same Kerberos/cache switches as getST, and LDAP tools do not all spell their LDAPS option the same way. -debug helps explain an error, while -ts adds timestamps to logs; neither changes your remote permissions.

Remote execution: what actually starts the process?

psexec — upload a service, start it, and communicate through named pipes

Windows administrators can manage services remotely. Impacket's PsExec implementation uses that ability and an embedded service executable called RemComSvc. SMB carries both the uploaded file and the RPC messages. SMB itself is not a universal “run this command” function.

impacket-psexec 'lab.example/labadmin@srv01.lab.example'
impacket-psexec 'lab.example/labadmin@srv01.lab.example' 'whoami'
impacket-psexec -k -no-pass -dc-ip 192.0.2.10 'lab.example/labadmin@srv01.lab.example' 'whoami'

The first command requests the default command interpreter. The second runs one command and returns its output. The third uses a suitable Kerberos cache instead of asking for a password. All three still need the same service and file permissions on the target.

  1. Authenticate to SMB and enumerate disk shares through the server service RPC interface.
  2. Find a writable share and upload the service executable. ADMIN$ is common, but the implementation can select another suitable writable disk share.
  3. Connect to the Service Control Manager through the svcctl named pipe, create a service whose executable path points to that upload, and start the service.
  4. Send the requested command to RemComSvc. The service launches the process and provides named pipes for input, output, and errors. Impacket connects those pipes to the terminal on Kali.
  5. Attempt to stop/delete the service and remove the uploaded executable when the session finishes.

Why does PsExec need write access?

The service executable must exist somewhere the target can execute it. Uploading it requires remote file write access. Creating and starting the service requires separate Service Control Manager permissions, normally obtained through an administrative account. An ordinary user with write access to a documents share cannot automatically create a Windows service. Likewise, service-management rights do not make an inaccessible share writable.

The service is normally created to run as LocalSystem, so its child process commonly reports nt authority\system. This follows from the service account, not from SMB magically upgrading the login. Remote UAC token filtering can also make a local administrator's network token less powerful than expected.

impacket-psexec 'lab.example/labadmin@srv01.lab.example' -c ./lab-check.exe
impacket-psexec 'lab.example/labadmin@srv01.lab.example' -path 'C:\Windows\System32' 'whoami'

-c uploads an additional local executable for the service to launch; it adds another file-transfer step. -path sets the remote working directory. -file is different: it replaces the embedded RemCom-compatible service executable. -service-name and -remote-binary-name select names, not permissions. Avoid colliding with an existing service: the service-install helper can remove a same-named service before creating its own.

For an assessment, distinguish “no writable share,” “access denied opening the service manager,” and “service started but pipes failed.” They are different stages. Uploads, service registration, process creation, and named-pipe activity are observable. Cleanup is attempted, not guaranteed, especially after interruption.

smbexec — use a service command line without uploading RemComSvc

impacket-smbexec 'lab.example/labadmin@srv01.lab.example'
impacket-smbexec 'lab.example/labadmin@srv01.lab.example' -mode SHARE -share 'C$'
impacket-smbexec 'lab.example/labadmin@srv01.lab.example' -shell-type powershell

SMBExec also talks to the Service Control Manager over an SMB named pipe. Instead of uploading a dedicated service executable, it creates a service whose command line invokes the target's existing command processor. In this implementation, that command line builds a temporary batch file, runs the requested command, redirects its output, and removes the batch file. The service is deleted after execution.

The default SHARE mode retrieves command output through a target share, normally C$. The second example makes that choice explicit. -shell-type powershell changes the command processor used for each request; it does not grant PowerShell-specific privileges. The resulting prompt is semi-interactive: commands are sent as separate remote executions, not a full interactive console with every terminal feature.

-mode SERVER starts an SMB server on Kali and has the target copy output back. That changes the return path and requires the target to reach Kali, plus permission to bind the local listening port. It does not remove service-creation requirements. “No uploaded service executable” also does not mean “no files written”: the batch file and output still matter. Processes normally run in the created service's LocalSystem context.

wmiexec — ask WMI to create a process, then collect its output

impacket-wmiexec 'lab.example/labadmin@srv01.lab.example' 'whoami'
impacket-wmiexec 'lab.example/labadmin@srv01.lab.example' -share 'ADMIN$' 'whoami'
impacket-wmiexec 'lab.example/labadmin@srv01.lab.example' -nooutput 'cmd.exe /c whoami'

WMI is Windows' management infrastructure. WMIExec authenticates through DCOM, connects to the WMI namespace, obtains Win32_Process, and calls its Create method. The execution path is DCOM/RPC, typically TCP 135 followed by a negotiated RPC endpoint. It does not install the PsExec service.

By default the command redirects output to a temporary file and Kali retrieves that file over SMB, usually through ADMIN$. That is why both RPC access and SMB access can matter. -share changes the output share. -nooutput avoids establishing the SMB output connection and is useful for a single command whose result you do not need to read back. It cannot provide the normal interactive prompt.

A successful process-creation call can coexist with failed output collection. If SMB is blocked or the selected share is inaccessible, “no output” is not proof that the command never ran. Check which stage failed before repeating a command that changes state. Remote WMI namespace and process-creation permissions are required, typically through administrator rights; the process normally uses the authenticated account's security context, not automatically LocalSystem.

-shell-type powershell changes the wrapper. -silentcommand invokes a supplied program without the usual cmd.exe output wrapper; shell built-ins such as dir are not standalone executables. -codec fixes text decoding when the remote code page differs from UTF-8, not authentication or execution.

dcomexec — execute through a remote COM object

impacket-dcomexec 'lab.example/labadmin@srv01.lab.example' -object MMC20 'whoami'
impacket-dcomexec 'lab.example/labadmin@srv01.lab.example' -object ShellWindows -nooutput 'cmd.exe /c whoami'

COM objects expose methods to applications, and DCOM lets a client activate or call some objects remotely. This tool uses supported objects such as MMC20, ShellWindows, or ShellBrowserWindow to reach an execution method. Changing -object changes the object and invocation path; it does not guarantee that the object exists, is registered for remote activation, or is accessible to your account.

Like WMIExec, the usual output path uses a temporary file and SMB retrieval. -nooutput removes that collection path for a one-shot command. The remote activation/access ACLs, account token, firewall, and DCOM hardening still apply. Process identity depends on the COM object's activation configuration; do not assume that every DCOM process will be SYSTEM. A failure to activate an object is different from a failed SMB file read.

atexec — create and run a scheduled task over RPC

impacket-atexec 'lab.example/labadmin@srv01.lab.example' 'whoami'
impacket-atexec -k -no-pass 'lab.example/labadmin@srv01.lab.example' 'hostname'

Despite its name, this implementation uses the Task Scheduler RPC interface, not merely the old at.exe command. It registers a temporary task, runs it, waits for completion, and attempts to remove it. The ordinary task definition runs as LocalSystem. Command output is normally redirected into a temporary file and retrieved using SMB.

The first example uses password authentication; the second selects Kerberos credentials already available to the tool. Both require permission to register and run the requested task. This is one-shot execution, so starting an interactive application does not turn the terminal into a full desktop session.

-session-id targets an existing logon session and changes the execution/output assumptions. -silentcommand avoids the normal command-processor wrapper and does not retrieve output. They are not general ways to bypass task permissions. An error reading the output file can happen after the task has already run. Task creation, execution, deletion, and temporary files can all be visible to defenders.

wmiquery — query management information without requesting a shell

impacket-wmiquery 'lab.example/alice@srv01.lab.example'
impacket-wmiquery 'lab.example/labadmin@srv01.lab.example' -namespace '//./root/cimv2' -rpc-auth-level privacy

This opens a WQL query shell through DCOM/WMI. A user can have delegated permission to query a namespace without being permitted to create processes. The second combination chooses a namespace and requests RPC packet privacy, which protects RPC message contents; some namespaces require that authentication level.

SELECT Caption, Version FROM Win32_OperatingSystem
SELECT Name, State, StartName FROM Win32_Service
describe Win32_Process

These are commands entered inside the WMI query shell. The first asks the OS class for selected properties. The second lists service state and configured service accounts. describe shows a class definition rather than executing a process. -file can read query-shell commands from a local file. The returned data helps explain the host, but querying an administrator-named service does not mean you can control it.

services — inspect or manage the Service Control Manager directly

impacket-services 'lab.example/labadmin@srv01.lab.example' list
impacket-services 'lab.example/labadmin@srv01.lab.example' config -name Spooler
impacket-services 'lab.example/labadmin@srv01.lab.example' status -name Spooler

This is a direct SCMR client over SMB/RPC. list enumerates services, config reads the selected service's configuration, and status reads its current state. Configuration can reveal an executable path, start mode, and service account. Service names are identifiers, not necessarily the friendly names shown in the Windows UI.

The other subcommands are start, stop, create, change, and delete. They request different access rights. create takes -name, -display, and -path; it registers a service but does not upload the executable to that path. A normal service executable must implement the Windows service protocol. change can modify a service's path or account only when the service ACL permits it. This helps explain why reading a service configuration is not proof of an exploitable service misconfiguration.

tstool — work with Remote Desktop Services sessions

impacket-tstool 'lab.example/labadmin@srv01.lab.example' qwinsta -v
impacket-tstool 'lab.example/labadmin@srv01.lab.example' tasklist

Terminal Services has RPC interfaces for session and process management. qwinsta enumerates sessions; -v asks for more detail. tasklist enumerates processes. This tool uses RPC over SMB named pipes, so it is not a graphical RDP client and does not simply connect to port 3389.

Other actions include taskkill, tscon, tsdiscon, logoff, msg, shadow, and shutdown. Session permissions and Windows policy govern them. A session ID identifies a session; it is not an authorization token. tscon attaches sessions, tsdiscon disconnects without the same meaning as logoff, and shadow requests a remote-assistance invitation; view/control and consent depend on its options and server policy. Shutdown affects the remote machine and all its sessions. These actions are state changes, unlike merely listing sessions.

Directory and RPC enumeration: learn what the identity can see

GetADUsers — read user objects through LDAP

impacket-GetADUsers 'lab.example/alice' -dc-ip 192.0.2.10 -all
impacket-GetADUsers 'lab.example/alice' -dc-ip 192.0.2.10 -user bob -all

Active Directory is a directory of objects and attributes. This tool authenticates to LDAP and requests user data such as account names, email addresses, and logon/password timestamps. Ordinary domain users can often read substantial directory information because applications need it to find people and services. This is not equivalent to reading their passwords.

-all includes users the default filter omits, including disabled accounts or accounts without an email address. The second example narrows the request to bob while retaining that broader inclusion behavior. Names and timestamps give context for further assessment; they do not prove that an account is active, privileged, or currently logged in. Some logon-related attributes are not an exact real-time record.

GetADComputers — read computer objects and optionally resolve their addresses

impacket-GetADComputers 'lab.example/alice' -dc-ip 192.0.2.10
impacket-GetADComputers 'lab.example/alice' -dc-ip 192.0.2.10 -resolveIP

A computer joined to AD has an account, usually ending in $, and directory attributes describing it. The first command queries those objects. The second also tries DNS resolution using the DC, connecting directory names to addresses. LDAP answers the object question; DNS answers the address question.

An object can remain after a machine is retired, and a DNS record can be stale. Neither means that a host is currently reachable or that its reported operating-system attributes are current. The unusually named -user filter in this script selects a specific account; check its help instead of inventing a -computer flag from another tool.

DumpNTLMInfo — inspect the identity information offered during NTLM negotiation

impacket-DumpNTLMInfo srv01.lab.example
impacket-DumpNTLMInfo srv01.lab.example -protocol RPC -port 135

An NTLM server challenge can include target information such as domain names, computer names, and version-related fields. This tool starts the negotiation and parses the response. The default example uses SMB. The second chooses RPC on TCP 135. It does not need to finish a valid user login just to inspect the challenge metadata that a server chooses to disclose.

For a pentester, this is useful when an IP is known but the AD naming context is not. Treat returned names as server-provided metadata. A successful negotiation is not successful authentication, an exposed NTLM challenge is not the password hash, and a version field alone is not proof of a vulnerability.

machine_role — ask a host about its role and primary domain

impacket-machine_role 'lab.example/alice@srv01.lab.example'
impacket-machine_role 'lab.example/alice@dc01.lab.example'

This uses the Directory Services setup RPC interface over an SMB named pipe to retrieve primary-domain information. It can distinguish roles such as member workstation, member server, or domain controller and return domain-related names. The two commands ask different hosts; they do not change either host's role.

This helps interpret later results: the local account database of a member server is different from the domain account database on a DC. Access depends on the server's RPC policy. A failure to query the role does not turn the target into an unknown operating system; it may simply mean the interface is blocked or restricted.

getArch — infer architecture through an RPC transfer-syntax negotiation

impacket-getArch -target srv01.lab.example
impacket-getArch -targets lab-hosts.txt -timeout 3

The script probes the RPC endpoint mapper and tests support for the NDR64 transfer syntax. Acceptance is an indication of a 64-bit RPC environment. It does not execute a binary on the host or read a CPU registry key. The first command probes one host; the second reads one hostname per line and adjusts the connection timeout.

This is a protocol-based inference, not a complete architecture inventory. A filtered port, unexpected RPC implementation, or negotiation error is not reliable proof of a 32-bit OS. Interpret the response in that context before choosing an architecture-specific lab payload.

lookupsid — translate candidate SIDs into account names

impacket-lookupsid 'lab.example/alice@dc01.lab.example' 2000
impacket-lookupsid 'lab.example/alice@srv01.lab.example' -domain-sids 2000

A Windows SID contains an authority/domain portion and a final relative identifier, or RID. LookupSID uses LSA RPC over SMB to learn the relevant SID namespace and ask which names correspond to candidate RIDs. This is account enumeration through SID translation, not password guessing.

The positional 2000 limits the RID search range, which also limits coverage and traffic. -domain-sids asks for domain SID handling instead of only the default local context and can result in lookups forwarded toward a DC. Anonymous or low-privilege translation is policy-dependent. Missing names beyond the selected range are not evidence that no other accounts exist.

samrdump — enumerate account metadata over SAMR

impacket-samrdump 'lab.example/alice@dc01.lab.example'
impacket-samrdump 'lab.example/alice@srv01.lab.example' -csv

SAMR is the remote account-management interface. This tool opens it over SMB and enumerates users and available account details. On a DC the relevant database can be the domain; on a member machine it can be local accounts. -csv changes output formatting for later analysis, not the remote access rights.

The word “dump” here means account metadata, not automatic NT-hash extraction. Modern remote SAM restrictions can deny the request to an otherwise valid user. Keep that distinction when reporting: listing an account and obtaining its reusable secret are very different outcomes.

rpcdump — enumerate registered RPC endpoints

impacket-rpcdump srv01.lab.example
impacket-rpcdump 'lab.example/alice@srv01.lab.example' -port 445

The endpoint mapper associates RPC interface identifiers with network endpoints. RPCDump asks it what is registered and prints UUIDs, versions, and bindings. The default example uses TCP 135; the second selects an SMB transport on 445. Other supported transports depend on the available server endpoints.

An interface being registered tells us where to direct an RPC bind. It does not prove that every operation on that interface is callable without authorization. This distinction is useful when a scanner finds an interface associated with a known technique: interface presence, usable method permissions, and vulnerable behavior are separate checks.

rpcmap — test RPC interfaces on a specific binding

impacket-rpcmap 'ncacn_ip_tcp:192.0.2.20[135]'
impacket-rpcmap 'ncacn_np:192.0.2.20[\pipe\srvsvc]' -auth-transport 'lab.example/alice'

A string binding describes how to reach RPC: ncacn_ip_tcp means TCP, while ncacn_np means a named pipe carried by SMB. RPCMap looks for interfaces that accept a bind at that location. The second command authenticates the SMB transport. RPC-level authentication can be configured separately with -auth-rpc; transport authentication and interface authentication need not be the same layer.

-uuid narrows the interface under test. -brute-uuids tries candidate interfaces, -brute-versions tests interface versions, and -brute-opnums sends operation probes. The last mode actually calls operation numbers and should not be described as a passive listing. -opnum-max and -version-max bound those probes. An accepted bind does not guarantee a useful, authorized operation.

net — query or change accounts and group membership through SAMR

impacket-net 'lab.example/alice@dc01.lab.example' user
impacket-net 'lab.example/alice@dc01.lab.example' user -name bob
impacket-net 'lab.example/labadmin@srv01.lab.example' localgroup -name Administrators

This is Impacket's SAMR implementation of familiar account-management tasks. user enumerates users; adding -name requests one account. localgroup selects an alias/local-group context, while group selects a domain-group context. The target host and the selected domain inside its account database determine what the names refer to.

The computer action works with computer accounts. Creation/removal and enable/disable options change objects; group -join and -unjoin change membership. Enumerating the Administrators group does not imply permission to join it. For each change, the SAMR server checks the rights on that account or group. An apparent “add user” command is still ordinary authenticated account management unless a specific authorization weakness has been demonstrated.

netview — query visible sessions and logged-on users

impacket-netview 'lab.example/alice' -target srv01.lab.example -noloop
impacket-netview 'lab.example/alice' -targets lab-hosts.txt -user bob -noloop

NetView combines SMB/RPC queries, including server session and workstation user information, to describe users visible on selected machines. It can enumerate domain targets when no target list is supplied. The examples deliberately select a host or file of hosts. -noloop stops after one probing pass; otherwise this tool can continue polling.

-user bob filters what is displayed; it does not log in as Bob or retrieve his credentials. -delay and -max-connections control repeated probing behavior. Permission restrictions can hide session data, and an SMB session is not necessarily an interactive desktop logon. These results are observations at a particular time, not proof that reusable credentials are in memory.

CheckLDAPStatus — infer LDAP signing and LDAPS channel-binding requirements

python3 /usr/share/doc/python3-impacket/examples/CheckLDAPStatus.py -domain lab.example -dc-ip 192.0.2.10
python3 /usr/share/doc/python3-impacket/examples/CheckLDAPStatus.py -domain lab.example -dc-ip 192.0.2.10 -timeout 5 -debug

This script first uses the supplied DNS/DC address to discover domain controllers through SRV records. It then probes the discovered DCs. -dc-ip therefore does not mean “only test this one host.” The timeout controls its DNS discovery timeout, and debug output helps explain the LDAP responses.

LDAP signing binds integrity protection to authenticated messages. Channel binding ties authentication to the TLS channel. The script infers enforcement from responses to deliberately incomplete or invalid authentication attempts; it does not read the effective policy directly. An NTLM-disabled server, a TLS problem, or an unexpected response can make that inference incomplete. A permissive-looking result is a starting point for relay analysis, not proof of a working relay path.

Kerberos: requesting tickets, inspecting them, and understanding delegation

Remember the normal process: a client authenticates to the KDC and receives a TGT plus session-key material. It uses that TGT to ask for a ticket to a particular service. The service ticket contains a part encrypted with the service account's key. Possessing a ticket file, decrypting its encrypted contents, and having the service authorize access are different things. These tools operate at different points in that process.

getTGT — request a ticket-granting ticket using an account secret

impacket-getTGT 'lab.example/alice' -dc-ip 192.0.2.10
impacket-getTGT 'lab.example/alice' -hashes ':<ALICE_NT_HASH>' -dc-ip 192.0.2.10
impacket-getTGT 'lab.example/alice' -aesKey '<ALICE_AES_KEY>' -dc-ip 192.0.2.10

These are three alternatives for authenticating as the same account: password, NT hash for a compatible RC4 path, or AES key. The tool builds an AS request, handles the supported pre-authentication exchange, and saves the returned credentials to a ccache file. This is an online conversation with the KDC, not local ticket forgery.

A normal successful run for Alice saves alice.ccache. Point KRB5CCNAME at that file before using a compatible tool with -k -no-pass. The cache contains more than the opaque TGT: it also carries the session key needed to create authenticators. Copying only ticket ciphertext is not the same as having a usable cache.

-principalType changes how the client principal is encoded, which can matter for enterprise names. -service requests a selected service in the AS exchange; it is a specialized mode, not a reason to treat getTGT and getST as interchangeable. A correct account secret can still fail because of account restrictions, an unsupported encryption type, time skew, or the wrong realm.

getST — request a service ticket, including supported delegation flows

export KRB5CCNAME="$PWD/alice.ccache"
impacket-getST -k -no-pass 'lab.example/alice' -spn cifs/srv01.lab.example -dc-ip 192.0.2.10
impacket-getST 'lab.example/websvc' -impersonate bob -spn cifs/srv01.lab.example -dc-ip 192.0.2.10

The first request uses Alice's TGT to ask for a ticket whose service principal is cifs/srv01.lab.example. CIFS is the service name normally used for SMB. A ticket for an HTTP SPN is not automatically an SMB ticket. The tool saves a ccache and prints its filename; use that actual filename when changing KRB5CCNAME, because the naming differs between modes and versions.

The second request means something different. websvc authenticates, while -impersonate bob asks for an S4U flow on Bob's behalf. S4U2Self requests a ticket to the service itself naming Bob; S4U2Proxy uses an appropriate evidence ticket to ask for a downstream service ticket. The KDC checks the delegation configuration and ticket properties. Knowing a random user's password does not grant permission to impersonate any account to any SPN.

-self stops at S4U2Self. -additional-ticket supplies an existing evidence ticket for the supported S4U2Proxy flow. -u2u requests user-to-user Kerberos, in which the ticket can be encrypted using a session key associated with another TGT. -altservice rewrites the service name in the produced credential; successful use still depends on the accepting service, its key, and validation. None of those switches creates missing delegation rights.

-renew asks the KDC to renew eligible credentials, subject to their renewal window. -force-forwardable relates to a historical ticket-modification technique and requires appropriate key material and compatible server behavior; it is not a universal bypass on patched DCs. -dmsa supports delegated managed service account handling. That mode depends on the relevant account configuration and DC behavior, which we return to in the BadSuccessor section.

GetNPUsers — identify accounts without pre-authentication and request AS-REP material

impacket-GetNPUsers 'lab.example/alice' -dc-ip 192.0.2.10
impacket-GetNPUsers 'lab.example/alice' -dc-ip 192.0.2.10 -request -format hashcat -outputfile asrep.txt
impacket-GetNPUsers 'lab.example/' -dc-ip 192.0.2.10 -usersfile lab-users.txt -no-pass -format hashcat -outputfile asrep.txt

Normally, pre-authentication makes the client prove knowledge of its secret before the KDC issues the normal AS reply. If an account has pre-authentication disabled, the KDC can return an AS-REP without that proof. Part of the reply is encrypted with a key derived from the account's password. A tester can take that ciphertext offline and check password guesses against it.

The first command uses Alice's credentials to discover matching accounts through LDAP. The second adds -request to obtain the encrypted reply material and writes it in a format understood by an offline cracking tool. The third already has candidate usernames in a file, so it can make AS requests without first authenticating to LDAP. The users-file path performs those requests; it does not need a separate LDAP enumeration phase.

This is AS-REP roasting, not Kerberoasting. The output commonly called a “hash” is a cracking representation of encrypted Kerberos material, not the target's reusable NT hash. Getting a response is not the same as recovering a password, and an empty result can mean pre-authentication is required, usernames are wrong, or the request failed. A strong password can remain impractical to recover even when the account setting is undesirable.

GetUserSPNs — find service accounts and request roastable service tickets

impacket-GetUserSPNs 'lab.example/alice' -dc-ip 192.0.2.10
impacket-GetUserSPNs 'lab.example/alice' -dc-ip 192.0.2.10 -request-user sqlsvc -outputfile sqlsvc-tgs.txt
impacket-GetUserSPNs 'lab.example/alice' -dc-ip 192.0.2.10 -request -save

An SPN maps a service name to an AD account. The first command queries LDAP for the relevant user accounts and SPNs. A normal authenticated domain user can often request a service ticket for a registered SPN even when the service will later deny that user access. Issuing the ticket and authorizing the service operation are separate decisions.

The ticket's service-encrypted part is protected by the service account's key. That gives an offline password-guessing target when the service account has a guessable password. The second example requests material for one selected account and writes the cracking representation. -request requests tickets for the enumerated targets; -save additionally saves requested credentials as caches. A saved credential cache and a hashcat/JtR text file serve different purposes.

-target-domain changes the domain being queried for supported cross-trust scenarios. -usersfile supplies a target account list. -machine-only and -request-machine select computer accounts in this snapshot; ordinary machine-generated passwords usually make password guessing much less practical than against human-chosen service passwords. Merely seeing an SPN is not proof of a weak password.

-no-preauth selects a specialized AS-exchange route using an account without pre-authentication; do not confuse it with -no-pass. The -stealth option changes the LDAP filter, not whether requests are logged, and can cause a much broader query. As pentesters, we should explain what the request actually does rather than treating an option's name as a promise.

findDelegation — read configured delegation relationships

impacket-findDelegation 'lab.example/alice' -dc-ip 192.0.2.10
impacket-findDelegation 'lab.example/alice' -dc-ip 192.0.2.10 -user websvc -disabled

Delegation lets one service act on behalf of a user when contacting another service. This tool queries LDAP for relevant account flags and attributes, including unconstrained delegation, constrained service lists, and resource-based constrained delegation information. The second command focuses on one account and includes disabled accounts that would otherwise be filtered out.

Unconstrained delegation, traditional constrained delegation, and RBCD place trust in different locations. A listed relationship does not mean the current tester controls the delegating account or can modify the target object. Check the account secret, the specific allowed service, sensitive-account restrictions, and whether the target is enabled. The tool enumerates configuration; it does not automatically obtain the downstream ticket.

getPac — request and decode authorization information using S4U2Self and U2U

impacket-getPac 'lab.example/alice' -targetUser bob
impacket-getPac 'lab.example/alice' -targetUser bob -hashes ':<ALICE_NT_HASH>'

A PAC is a collection of authorization data carried in Windows Kerberos tickets, including domain and group information. This example combines S4U2Self with user-to-user Kerberos so that it can decrypt the returned ticket using session-key material it possesses and inspect the PAC. The second form changes the secret used for Alice's authentication; Bob remains the subject whose PAC is requested.

Reading Bob's group information is not equivalent to receiving permission to act as Bob at arbitrary services. The KDC decides whether the request is valid. This script has a smaller option set than getST: it does not expose -dc-ip or the common -k -no-pass combination in the reviewed snapshot, so domain resolution must work as expected. Do not manufacture unsupported flags from a similar-looking tool.

describeTicket — inspect a saved ticket and optionally decrypt its encrypted part

impacket-describeTicket alice.ccache
impacket-describeTicket service.ccache --aes '<SERVICE_ACCOUNT_AES_KEY>'
impacket-describeTicket service.ccache --rc4 '<SERVICE_ACCOUNT_NT_HASH>'

These commands work on local files. Without a service key, the tool can describe the cache and ticket metadata that is available. Supplying the matching AES or RC4 service key lets it attempt to decrypt the ticket's encrypted part and parse the PAC. The key must match both the account behind the ticket's service and the ticket's encryption type.

For a service ticket that usually means the service account's key; for an ordinary TGT it means the appropriate krbtgt key. Alice's password is not a universal key for every ticket she receives. Password-based derivation options need the proper account, realm, and salt. --asrep-key has a different purpose: decrypting PAC credential information when that structure is present. Parsing a file does not establish that a live service would accept it.

ticketConverter — convert between Kerberos credential containers

impacket-ticketConverter alice.kirbi alice.ccache
impacket-ticketConverter alice.ccache alice.kirbi

A Windows-style KRB-CRED file, often called .kirbi, and a ccache file package credentials differently. This utility converts the container so another client can use the same underlying ticket and session key. The two positional arguments are input and output; the tool detects the supported input format.

Conversion is local. It does not renew a ticket, change its identity, add group membership, recover a missing password, or make an expired ticket valid. Before using the output, inspect the principal, service, validity period, and encryption context. A different filename extension does not change what the KDC issued.

ticketer — construct tickets using key material already under your control

impacket-ticketer -domain lab.example -domain-sid S-1-5-21-111111111-222222222-333333333 -aesKey '<LAB_KRBTGT_AES_KEY>' -user-id 1105 -groups 513 -duration 1 alice
impacket-ticketer -domain lab.example -domain-sid S-1-5-21-111111111-222222222-333333333 -spn cifs/srv01.lab.example -aesKey '<LAB_SERVICE_AES_KEY>' -user-id 1105 -groups 513 -duration 1 alice

These examples assume the signing/encryption keys and identifiers were already obtained in an authorized lab. Without -spn, Ticketer constructs a TGT, commonly called a golden ticket, using the relevant krbtgt key. With -spn, it constructs a service ticket, commonly called a silver ticket, using the service account's key. It does not discover those keys for us.

-domain-sid provides the domain SID; -user-id provides the account RID; -groups supplies group RIDs in the PAC; and -duration sets the requested lifetime in hours. The examples deliberately specify these values instead of silently accepting the tool's privileged default group list and long lifetime. Inventing a name or group value does not guarantee acceptance by a hardened service or KDC.

-request, together with authentication options such as -user and -password, requests an initial ticket and uses it as a template. -impersonate supports the tool's sapphire-ticket flow, using S4U2Self/U2U-derived PAC material. -extra-sid changes extra SID claims. Those modes still depend on the keys, protocol behavior, account relationships, and PAC validation in the environment. Ticket creation success is only evidence that a local file was created; the meaningful test is the narrowly authorized service operation it can actually perform.

keylistattack — use an RODC key in a Kerberos key-list request

impacket-keylistattack LIST -domain lab.example -kdc dc01.lab.example -rodcNo 123 -rodcKey '<LAB_RODC_KRBTGT_AES_KEY>' -t labuser

A read-only domain controller has its own krbtgt-derived identity and password-replication rules. This technique uses the relevant RODC krbtgt key to construct credentials for a KERB-KEY-LIST request to a writable KDC. The critical prerequisite is that key and its correct RODC identifier. An ordinary domain user password alone is insufficient.

LIST means the target account names are supplied rather than discovered through an SMB account-enumeration phase. -t selects one user, -tf supplies a file, -domain supplies the realm, and -kdc supplies the KDC. -rodcNo and -rodcKey must correspond to the same RODC context.

The KDC's replication restrictions and server behavior determine which accounts can return useful key material. The credential-target form can enumerate accounts first; -full broadens attempts and can produce many rejected requests. This is different from password guessing and from ordinary LDAP password reads. A result reflects the impact of compromised RODC key material, not a general unauthenticated domain-dump feature.

Credential material: identify where the secret is stored

secretsdump — read protected local stores or request directory replication

impacket-secretsdump 'lab.example/labadmin@srv01.lab.example' -outputfile srv01-secrets
impacket-secretsdump 'lab.example/auditor@dc01.lab.example' -just-dc-user labuser -just-dc-ntlm
impacket-secretsdump -sam SAM.copy -system SYSTEM.copy -security SECURITY.copy LOCAL

These commands select three distinct situations. The first authenticates to a member server and attempts to obtain local SAM information and LSA secrets/cached logon data using privileged remote access. The second requests selected directory secret material from a DC through DRSUAPI replication; auditor must have the necessary replication permissions. The third parses already acquired local registry-hive copies and makes no remote connection.

Why does SYSTEM matter when reading SAM?

The SAM hive stores local account password material in protected form. The SYSTEM hive contains information used to derive the boot key needed for the decryption process. SECURITY has other protected LSA data and cached domain-logon material. These files play different roles: simply holding SAM bytes does not mean those bytes contain printable passwords. For offline AD extraction, -ntds selects an acquired NTDS database and the matching decryption context is still needed.

Why can DCSync work without a shell on the DC?

Domain controllers need to replicate directory changes. DRSUAPI exposes that replication protocol, including operations such as DRSGetNCChanges. A caller with the required directory replication rights can request protected attributes through that interface. This path does not need to upload PsExec's service or read NTDS.dit as an SMB file. Replication rights are the authority being exercised. Local administrator rights on a member server do not provide them.

-just-dc-user narrows replication to one user in the supported DRS path. -just-dc selects directory credentials instead of the local SAM/SECURITY phase, and -just-dc-ntlm limits directory output to NTLM material. -ldapfilter narrows users through an LDAP filter in the supported mode. Filters restrict requested output; they do not supply missing replication permissions.

The default remote local-store path can start or temporarily reconfigure RemoteRegistry, save hive data, and read files back. -use-vss instead selects an NTDS snapshot/acquisition path that requires privileged remote execution and creates artifacts. -exec-method controls that execution method where applicable. The -use-remoteSSWMI family creates and reads a remote shadow copy through WMI; it is also an active acquisition method, not just a query.

-use-keylist selects the specialized RODC key-list path with the corresponding RODC material. -history requests older stored secrets, -outputfile chooses an output basename, and -resumefile supports the DRS replication workflow. These modes have different prerequisites; combining flags from incompatible paths does not make them interchangeable.

Keep the output types separate. Local/domain NT hashes may be reusable in compatible authentication protocols. Cached domain-logon hashes are generally offline-verification targets and cannot simply be passed to -hashes. Kerberos AES keys and LSA secrets have their own uses. The tool does not read every logged-on user's LSASS memory just because its name contains “secrets.”

regsecrets — read SAM and LSA data through privileged registry operations

python3 /usr/share/doc/python3-impacket/examples/regsecrets.py 'lab.example/labadmin@srv01.lab.example' -outputfile srv01-registry
python3 /usr/share/doc/python3-impacket/examples/regsecrets.py 'lab.example/labadmin@srv01.lab.example' -nosam -nocache

This separate example uses the Remote Registry path and registry backup/restore access options to retrieve protected values. It focuses on SAM, cached logon data, and LSA secrets rather than providing the DRS domain-replication interface. Its implementation reads the needed registry data directly instead of treating every operation as a full hive-file export.

The first example selects an output basename. The second skips SAM and cached-logon processing, leaving the LSA-secret path; -nolsa disables that path as well. -throttle adds a delay between operations, and -history requests supported older values. RemoteRegistry can still need to be enabled or started, and administrative/backup-related privileges still matter. Fewer exported files do not make the access unaudited or remove the credential sensitivity of the result.

Get-GPPPassword — find and decrypt old Group Policy Preferences cpassword values

impacket-Get-GPPPassword 'lab.example/alice@dc01.lab.example' -share SYSVOL
impacket-Get-GPPPassword LOCAL -xmlfile ./Groups.xml

Group Policy Preferences historically stored some configured passwords in XML files using an encryption key that became publicly known. Since domain clients must read policy files, those XML files can be readable in SYSVOL. When a leftover cpassword value is present, the tool can decrypt it locally; it does not brute-force the password.

The first command searches the selected SMB share. -base-dir can narrow the search beneath a known directory. The second parses an already acquired XML file without connecting to a DC. Modern policy editing no longer provides the same old password-storage mechanism, but obsolete files can remain. A recovered password can also be stale: reading a historical configured secret does not prove it still authenticates.

GetLAPSPassword — read local administrator passwords delegated through AD

impacket-GetLAPSPassword 'lab.example/helpdesk' -dc-ip 192.0.2.10 -computer SRV01
impacket-GetLAPSPassword 'lab.example/helpdesk' -dc-ip 192.0.2.10 -computer SRV01 -ldaps -outputfile srv01-laps.txt

LAPS manages per-machine local administrator passwords and stores related data in Active Directory with controlled access. This tool queries the supported legacy and Windows LAPS attributes. The first example selects one computer. The second uses LDAPS and writes the result to a file. -computer is a directory account filter, not a request to log in to the local administrator account.

For encrypted Windows LAPS data, the implementation can use MS-GKDI to obtain the authorized key material needed for DPAPI-NG decryption. Being able to read an encrypted attribute is not necessarily enough to decrypt it. LDAP access rules, the configured authorized decryptors, and RPC connectivity can all matter. LDAPS protects the transport; it does not grant permission to read another machine's password.

The pentesting question is whether the current identity can retrieve passwords beyond its intended administration scope. A password returned to an intentionally authorized helpdesk group is not automatically a vulnerability. Check the managed account name, machine, expiration information, and access delegation before describing the impact.

dpapi — decrypt Windows-protected data when the corresponding key context is available

impacket-dpapi masterkey -file ./masterkey.bin -sid S-1-5-21-111111111-222222222-333333333-1105
impacket-dpapi credential -file ./credential.bin -key '<DECRYPTED_MASTERKEY_HEX>'
impacket-dpapi unprotect -file ./blob.bin -key '<DECRYPTED_MASTERKEY_HEX>' -entropy 'lab-application-context'

DPAPI lets Windows applications protect data using a user or machine context. Applications usually encrypt their data with a master key, while that master key is itself protected using user/system/domain recovery mechanisms. This is why “I copied the browser or credential file” is only the beginning of the decryption problem.

The first example parses a master-key file and, with the SID supplied, can prompt for the user password to try the relevant derivation. -password, -key, -pvk, or matching SYSTEM/SECURITY material select other supported ways to unlock a master key. The second example supplies a decrypted master key to a credential-file parser. The third uses the same idea for a DPAPI blob whose application also supplied extra entropy. Wrong entropy can cause decryption failure even with the right master key.

vault works with vault policy/credential files; credhist deals with protected credential history. The separate backupkeys action connects to a domain controller for domain DPAPI backup-key operations, with --export writing key material. It requires the appropriate high-privilege access. That online operation is different from parsing a local file, and none of these actions bypasses missing cryptographic inputs by itself.

mimikatz — connect to an existing Mimikatz RPC server

impacket-mimikatz 'lab.example/labadmin@srv01.lab.example'
impacket-mimikatz 'lab.example/labadmin@srv01.lab.example' -file ./lab-rpc-commands.txt

The name is easy to misunderstand. This script is a client for the remote Mimikatz RPC server interface. It expects a compatible server to be running already, locates/connects to that RPC interface, performs its protocol handshake, and forwards commands. It does not upload Mimikatz or turn every Windows machine into a Mimikatz server.

The first form opens the mini shell; the second reads commands from a local file. The actual command capabilities and security context come from the server-side component and its privileges. If the interface is absent, an administrator password alone will not create it. Explain that prerequisite before presenting this as a credential-access option.

Changing directory objects: which permission authorizes the change?

addcomputer — create or manage a computer account through SAMR or LDAPS

impacket-addcomputer 'lab.example/alice' -dc-ip 192.0.2.10 -method SAMR -computer-name 'LABPC01$' -computer-pass '<NEW_LAB_MACHINE_PASSWORD>'
impacket-addcomputer 'lab.example/alice' -dc-ip 192.0.2.10 -method LDAPS -computer-name 'LABPC02$' -computer-pass '<NEW_LAB_MACHINE_PASSWORD>'

These examples create directory computer accounts, not virtual machines. A machine account has a secret just like a user account, but its account type and role differ. Whether Alice can create one depends on account-creation rights, applicable quota, container permissions, and domain policy. A commonly seen default quota is not a guarantee for the assessed domain.

SAMR uses account-management RPC over SMB, while LDAPS uses LDAP over TLS. The LDAPS method can select a container with -computer-group and a base distinguished name with -baseDN. The paths do not populate every attribute identically: for example, the SAMR-created account can need later DNS/SPN configuration. Creating the object is not a complete Windows domain join.

-computer-name selects the account; the quotes preserve the final dollar sign. -computer-pass establishes the new account's secret. -no-add instead changes the password of an existing computer account, and -delete removes one. Both are real changes that can break an existing machine's relationship with the domain. Owning a newly created machine account also does not by itself give that machine delegation rights to another server.

changepasswd — distinguish a password change from an administrative reset

impacket-changepasswd 'lab.example/labuser@dc01.lab.example' -protocol smb-samr -newpass '<NEW_LAB_USER_PASSWORD>'
impacket-changepasswd 'lab.example/labuser@dc01.lab.example' -protocol kpasswd -newpass '<NEW_LAB_USER_PASSWORD>'

Both examples change the selected lab account's password using the supported protocol. A normal change generally proves knowledge of the current secret. An administrative reset instead relies on reset authority over the account. Those are distinct server operations, with different effects on policy checks and sometimes on access to previously protected user data.

smb-samr carries SAMR over SMB, rpc-samr uses the corresponding RPC transport, kpasswd uses the Kerberos password-change service, and ldap uses the directory password operation through the script's protected LDAP connection. -reset selects privileged reset behavior. -altuser with its password/hash option supplies an alternate identity for supported operations; it does not grant that identity reset rights.

-newpass is the replacement plaintext secret. -newhashes is a different input supported only by compatible methods; it should not be treated as an option that works with every protocol. The credentials in the target string identify the account whose password is being changed. This is an account mutation, not a credential-validity check.

dacledit — read and edit the permissions attached to an AD object

impacket-dacledit 'lab.example/alice' -dc-ip 192.0.2.10 -action read -target labgroup
impacket-dacledit 'lab.example/labadmin' -dc-ip 192.0.2.10 -action backup -target labgroup -file labgroup-before.json
impacket-dacledit 'lab.example/labadmin' -dc-ip 192.0.2.10 -action write -target labgroup -principal alice -rights WriteMembers

A DACL contains access-control entries describing which principals are allowed or denied particular operations on an object. The first command reads the group's DACL. The second saves a copy. The third adds a permission allowing Alice to write membership on that lab group, provided the authenticating account can modify its DACL. It does not immediately add Alice to the group.

-target selects the object being protected; -principal selects who receives the entry; the identity argument authenticates the editor. These can be three different accounts/objects. SID and distinguished-name alternatives avoid ambiguous names. -rights chooses known rights, while -rights-guid and the custom-mask options address more specific cases.

ResetPassword grants a particular extended right, WriteMembers affects membership, and DCSync represents replication-related rights when applied in the correct directory context. They are not interchangeable forms of “admin.” -inheritance changes how an entry can flow to child objects; protected objects and inheritance rules can prevent the expected effect. remove removes matching entries, and restore writes a saved DACL back. Restoring an old backup can also overwrite legitimate intervening changes, so the before/after security descriptor matters.

owneredit — read or change the owner in an AD security descriptor

impacket-owneredit 'lab.example/alice' -dc-ip 192.0.2.10 -action read -target labgroup
impacket-owneredit 'lab.example/labadmin' -dc-ip 192.0.2.10 -action write -target labgroup -new-owner alice

The owner is a security-descriptor field separate from the DACL. The first example inspects it; the second requests an ownership change to Alice. The authenticating account must have the necessary owner-changing authority, and server rules can restrict which new owner can be assigned.

Ownership is valuable because it commonly carries the ability to adjust the DACL, subject to owner-rights and other applicable controls. It is not the same as immediately becoming a group member or receiving all object rights. This explains a familiar assessment relationship: permission to take ownership can enable a later permission change. Document the exact object and resulting authority rather than claiming that every ownership change equals domain administration.

rbcd — inspect or edit the target resource's delegation permission

impacket-rbcd 'lab.example/alice' -dc-ip 192.0.2.10 -delegate-to 'SRV01$' -action read
impacket-rbcd 'lab.example/labadmin' -dc-ip 192.0.2.10 -delegate-to 'SRV01$' -delegate-from 'LABPC01$' -action write

Resource-based constrained delegation stores the relevant trust decision on the resource account, in msDS-AllowedToActOnBehalfOfOtherIdentity. The first command reads that attribute's security descriptor on SRV01. The second permits the selected delegating account in that descriptor, if the editor has the necessary write authority over the target object.

-delegate-to is the account representing the resource; -delegate-from is the account intended to act on another user's behalf. Reversing them changes the meaning. Writing the attribute does not itself authenticate as the delegating account or request an S4U service ticket. Those are later Kerberos operations with their own prerequisites and restrictions.

-action remove removes the selected delegation entry, whereas flush clears the attribute's delegation configuration more broadly. They are not equivalent cleanup operations. Preserve the original descriptor and account for existing entries. A user who can read this configuration may still have no ability to change it or use the delegating account.

badsuccessor — inspect dMSA relationships and understand the account-migration trust

python3 /usr/share/doc/python3-impacket/examples/badsuccessor.py 'lab.example/alice' -dc-ip 192.0.2.10 -action search
python3 /usr/share/doc/python3-impacket/examples/badsuccessor.py -h

Delegated managed service accounts, or dMSAs, support managed service identity and migration from predecessor accounts. This script deals with those objects and their migration-related attributes. The first command selects its search action; the second exposes the exact options in the installed snapshot. Search output is information about objects and permissions, not proof that the domain is vulnerable.

The important theoretical relationship is that control over a dMSA and its migration linkage can be interpreted by a vulnerable KDC as authority associated with a predecessor identity. That interpretation depends on DC version, patch state, directory permissions, and the resulting account state. Having a writable OU by itself should not be reported as a demonstrated takeover on every current deployment.

The script's other actions are add, modify, and delete. -target-ou selects a directory container, -dmsa-name selects the dMSA, -target-account selects its intended predecessor, and -principals-allowed identifies an account allowed to retrieve the managed password. These are directory changes, and creation, modification, password retrieval, and KDC ticket issuance each have their own permission checks. The getST -dmsa mode participates in the related Kerberos handling; the LDAP tool does not itself provide a remote shell.

SMB and registry access: read, write, and host files

smbclient — interact with shares using the authenticated identity

impacket-smbclient 'lab.example/alice@srv01.lab.example'
impacket-smbclient -k -no-pass 'lab.example/alice@srv01.lab.example' -inputfile ./share-commands.txt -outputfile ./share-session.txt

This opens Impacket's SMB mini shell. It negotiates SMB, authenticates, and sends share/file operations. The second example obtains credentials through Kerberos, reads mini-shell commands from a local file, and logs the session. A batch file of commands can include writes as well as reads, so know what it contains.

shares
use Public
ls
cd Reports
get assessment.txt
exit

These commands are entered inside the SMB shell. shares lists shares, use selects one, ls lists its current directory, and get downloads an allowed file. put uploads a file; mkdir, rm, and rmdir change remote storage. The mini shell manages files and is not an operating-system shell on the Windows host.

Access is affected by both share permissions and underlying filesystem permissions. A successful share connection does not prove access to every directory, and a writable share does not prove administrative execution. IPC$ is used for interprocess communication/named pipes rather than acting like an ordinary documents share.

smbserver — serve a local directory from Kali

sudo impacket-smbserver LABSHARE ./lab-share -smb2support -ip 192.0.2.50 -username labtransfer -password '<LAB_TRANSFER_PASSWORD>'

This command starts a server on Kali. LABSHARE is the name a client sees, and ./lab-share is the existing local directory backing it. -ip selects the listening address. The SMB2 option enables the tool's SMB2 support, which matters when clients reject SMB1. Binding the normal TCP 445 port can require elevated local privileges; that is why this example uses sudo.

The username/password configure authentication to this temporary server; they are not automatically AD domain credentials. A Windows client can address it as \\192.0.2.50\LABSHARE if routing, firewall, SMB policy, and authentication permit. Client signing/encryption requirements and guest restrictions can prevent a connection even when the port is open. The implementation is a testing server, not a full Windows SMB server with every security feature.

-port changes the listener, but an ordinary Windows UNC path does not automatically select an arbitrary alternate SMB port. The server may also log NTLM challenge-response material from clients. Such material is not the client's raw NT hash. Hosting a share does not execute any file on a client merely because the client connects.

karmaSMB — return selected local file content for SMB requests

sudo impacket-karmaSMB ./lab-marker.txt -smb2support
impacket-karmaSMB --help

KarmaSMB is a specialized SMB server example. Instead of serving a normal directory tree in the usual way, it returns the chosen local file's contents for incoming file requests. The first example therefore supplies a plain marker file. -config can map requested filename extensions to different local files; requests without a mapping use the default file.

This helps study how a client consumes a file it believes came from an SMB path. The client still needs to be directed to this server by an independently established lab setup. Receiving bytes does not automatically execute them: execution depends on what the client application does with that file. The server binds a listening port and handles authentication traffic, so it is a server-side experiment rather than a read-only remote enumeration tool.

reg — query or modify the live remote registry

impacket-reg 'lab.example/labadmin@srv01.lab.example' query -keyName 'HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion' -v ProductName
impacket-reg 'lab.example/labadmin@srv01.lab.example' query -keyName 'HKLM\SOFTWARE\LabApp' -s

This uses the Remote Registry RPC interface over SMB to operate on the remote registry. -keyName selects a key, -v selects a value, and -s recursively queries below the selected key. Access is checked against the registry and remote-management permissions. The helper may start or temporarily enable RemoteRegistry when its workflow requires it, so even a query-oriented invocation can affect that service state.

add and delete modify keys or values; -vt and -vd specify type and data for a supported write. save asks the remote machine to export a selected hive/key, while backup targets the SAM, SYSTEM, and SECURITY hives. Their -o value is an output UNC path used by the target, not simply a local Kali filename. That requires the target to reach and write to the destination.

A successful registry read is not permission to change the same key, and saving credential hives requires additional privileges. Read the scope of each action before treating this as the equivalent of opening a local text file.

registry-read — inspect an acquired registry hive offline

impacket-registry-read ./SOFTWARE.copy enum_key -name '\Microsoft'
impacket-registry-read ./SOFTWARE.copy enum_values -name '\Microsoft\Windows NT\CurrentVersion'
impacket-registry-read ./SOFTWARE.copy get_value -name '\Microsoft\Windows NT\CurrentVersion\ProductName'

These examples parse a local binary registry-hive copy. enum_key lists subkeys, enum_values lists values at one key, and get_value reads one named value. Paths are relative to the root of the acquired hive, so SOFTWARE.copy does not need an extra HKLM\SOFTWARE prefix inside every path.

-recursive expands supported enumeration, walk traverses a subtree, and get_class reads a key's class metadata. This tool does not authenticate to Windows or acquire the hive. The ability to read an offline copy comes from the earlier acquisition step; encrypted secrets inside it can still require the appropriate keys and another parser.

attrib — query or change SMB file attributes

python3 /usr/share/doc/python3-impacket/examples/attrib.py 'lab.example/alice@srv01.lab.example' Public 'Reports\assessment.txt' query

This sends SMB file-information operations for one path on one share. The target identity, share name, and path are separate positional arguments; query reads attribute flags such as archive, hidden, or read-only. Those flags describe file behavior and presentation, not its entire security descriptor.

The set action writes supported attribute flags; options such as --readonly, --hidden, and --normal select the intended values. That action needs file-attribute write permission and may replace the set of flags rather than merely displaying it. Marking a file read-only is not a replacement for a restrictive DACL, and setting an encrypted/compressed-looking attribute is not proof that a complete data transformation happened. Server support and resulting file information must be checked.

filetime — inspect or modify SMB file timestamps

python3 /usr/share/doc/python3-impacket/examples/filetime.py 'lab.example/alice@srv01.lab.example' Public 'Reports\assessment.txt' stat

The stat action asks SMB for the selected file's timestamp fields, including creation, access, write, and change time. Those fields describe different events; change time is not simply another name for the last content-write time. A filesystem, application, or backup process can also affect how timestamps are maintained.

The touch action changes selected fields when the account has attribute-write permission. --timestamp supplies a value, --reference selects another share/path whose times are copied, and --validate reads the result back. This is an integrity-impacting write, not passive inspection. For an assessment, first understanding who can alter metadata helps explain why a timestamp alone is weak evidence of when a file was created or used.

Relay and application protocols

ntlmrelayx — forward an NTLM authentication exchange to another service

NTLM is a challenge-response protocol. The client calculates a response using its secret and the server's challenge. In a relay, the intermediary forwards the target server's challenge to the client, then forwards the client's answer back to that target. The intermediary can authenticate a connection as the client without learning its password, if the protocol protections and endpoint policies permit the exchange.

sudo impacket-ntlmrelayx -t smb://srv01.lab.example -smb2support -i --no-http-server --no-wcf-server --no-raw-server --no-rpc-server --no-winrm-server

Here -t selects one SMB destination, -smb2support enables SMB2 on the receiving server, and -i requests an interactive session after a successful supported relay. The server-disabling flags leave the SMB listener as the selected receiving path. This command waits for incoming authentication; it does not itself make a client connect or discover a password. An independently configured lab client must authenticate to the listener.

Why can a relay authenticate successfully but still fail to execute?

The relayed identity keeps its permissions at the destination. An ordinary account may read an allowed share but lack access to the service manager or protected registry data. “Relay succeeded” therefore does not mean “administrator shell.” Requiring SMB signing at the destination can prevent ordinary SMB relay use because the intermediary lacks the signing key needed for subsequent messages. LDAP signing, LDAPS channel binding, HTTP extended protection, and NTLM restrictions protect different paths. Enabling TLS alone is not the same as correctly binding NTLM authentication to that TLS channel.

sudo impacket-ntlmrelayx -t ldap://dc01.lab.example -i --no-http-server --no-wcf-server --no-raw-server --no-rpc-server --no-winrm-server
sudo impacket-ntlmrelayx -tf lab-relay-targets.txt -smb2support -socks --no-http-server --no-wcf-server --no-raw-server --no-rpc-server --no-winrm-server

The LDAP example changes the destination protocol and asks for its interactive console, where the relayed identity's directory permissions apply. The targets-file example reads protocol-qualified destinations from a file and asks supported relay clients to preserve authenticated sessions for SOCKS use. SOCKS mode reuses specific established identities and connections; it is not a general-purpose proxy that grants arbitrary authentication to any host. -socks-address and -socks-port control that local interface.

Post-authentication behavior is important. A bare SMB relay can attempt secret dumping by default in this implementation; -c requests command execution and -e supplies an executable. LDAP modes can enumerate or attempt directory changes. --no-dump, --no-da, and --no-acl control particular LDAP actions; they are not universal read-only switches for every protocol. Read the selected module's behavior before assuming that starting a listener merely captures traffic.

The larger option set selects additional protocol-specific actions: -q sends SQL queries; --dump-laps and --dump-gmsa request readable managed-password data; --delegate-access writes delegation configuration when permitted; and --shadow-credentials changes key-credential data on an authorized target object. Each depends on the relayed account's actual authority, not just on possession of an NTLM response.

--adcs selects certificate-enrollment relay behavior, with --template choosing an enrollment template. The endpoint's authentication protections, enrollment permissions, and template configuration determine whether a useful certificate can be issued. --rpc-attack and -rpc-mode select supported task/certificate RPC paths. SCCM-specific options target management-point policies or distribution-point content. These are separate workflows, not flags to append together until something succeeds.

Historical switches such as --remove-mic rely on particular vulnerable protocol behavior. They do not generally defeat current signing or channel-binding enforcement. For a useful finding, record the source identity, destination protocol, protection that was missing, and concrete operation allowed after authentication. Capturing a challenge-response string alone is not that finding.

mssqlinstance — ask SQL Browser which instances are advertised

impacket-mssqlinstance sql01.lab.example
impacket-mssqlinstance sql01.lab.example -timeout 3

SQL Server Browser can answer SQL Server Resolution Protocol queries over UDP 1434 with instance names and connection information. This helps when a named SQL instance listens on a dynamic TCP port instead of 1433. The second example changes how long the tool waits for a response.

This is discovery, not a database login. A silent response can mean SQL Browser is disabled or UDP is filtered even while the database service is reachable. Use the returned endpoint information with a database client; do not confuse the Browser UDP port with the TDS port used for actual SQL queries.

mssqlclient — authenticate through TDS and understand the SQL execution context

impacket-mssqlclient 'lab.example/alice@sql01.lab.example' -windows-auth
impacket-mssqlclient 'sqlaudit@sql01.lab.example' -port 1433 -db master

SQL Server speaks Tabular Data Stream, or TDS. The first command requests Windows authentication, where the server validates a Windows identity. The second uses a SQL login and selects a database. These identities are not interchangeable: a Windows password may be valid for the domain yet have no SQL login permission, while a SQL-only account may have no Windows logon rights.

SELECT SYSTEM_USER AS login_name, USER_NAME() AS database_user;
SELECT IS_SRVROLEMEMBER('sysadmin') AS is_sysadmin;
enum_db
enum_links
enum_impersonate

These lines belong inside the SQL client. SQL Server distinguishes the server login from the user mapped inside a database. The queries show those contexts and whether the current context is a sysadmin. The client helpers enumerate databases, linked servers, and potential impersonation relationships using SQL queries. -show helps reveal the queries sent by helpers, and -file reads SQL-shell commands from a file.

How does a SQL connection become an operating-system command?

xp_cmdshell is a SQL Server extended procedure that can launch an OS command when enabled and permitted. Impacket's helper calls that procedure; TDS itself does not launch a Windows shell. A sysadmin invocation normally uses the SQL Server service account, while an authorized non-sysadmin invocation needs the configured proxy account. That account might be a low-privilege service identity, a domain account, or something more powerful; inspect the result rather than assuming SYSTEM.

xp_cmdshell whoami

This single helper command asks an already permitted and enabled xp_cmdshell to report its Windows identity. enable_xp_cmdshell changes server configuration and needs sufficient SQL privileges; it is not a harmless prerequisite to run automatically. exec_as_login and exec_as_user change supported SQL security contexts only when impersonation is allowed. use_link traverses a linked-server relationship whose login mapping and RPC configuration determine the next authority.

Helpers that upload/download files or start SQL Agent jobs depend on further database and OS capabilities. A shell helper prefixed with ! runs locally on Kali; it is not proof of remote execution. Separate SQL data access, SQL privilege escalation, and OS command execution in both reasoning and reporting.

exchanger — query Exchange address-book information through NSPI

impacket-exchanger 'lab.example/alice@exchange.lab.example' nspi list-tables -count
impacket-exchanger 'lab.example/alice@exchange.lab.example' nspi dump-tables -name GAL -lookup-type MINIMAL -rows-per-request 50

The Name Service Provider Interface exposes address-book information used by Exchange clients. This tool reaches the supported NSPI/RPC-over-HTTP path. list-tables enumerates address books and -count asks for their sizes. dump-tables requests records from the selected address book; GAL refers to the global address list, where supported by the server's naming.

-lookup-type selects how much record data to request, and -rows-per-request sets batching rather than a total result limit. -rpc-hostname supplies the backend RPC identity when the public Exchange hostname alone is insufficient. DNS, RPC proxy configuration, and account permissions all matter.

The guid-known action requests objects by supplied GUID, while dnt-lookup iterates distinguished-name tags across a selected range. These modes can reveal directory information exposed through Exchange. They are not mailbox-message download commands, nor do they prove that LDAP is equally accessible from the same network position.

rdp_check — test the supported RDP authentication negotiation

impacket-rdp_check 'lab.example/alice@srv01.lab.example'
impacket-rdp_check 'lab.example/alice@srv01.lab.example' -hashes ':<ALICE_NT_HASH>'

This example speaks enough RDP/CredSSP-related negotiation to test credentials against the target, normally on TCP 3389. It does not render a desktop. The second form supplies NT-hash material to its supported authentication path; acceptance also depends on server capabilities and policy, rather than hashes being universally usable for every RDP logon.

An authentication-stage result should not be stretched into proof of a usable interactive desktop. Remote-interactive logon rights, account restrictions, session policy, and later protocol stages can still matter. -6 selects IPv6 support. A protocol negotiation failure can be different from an invalid password, especially with modern CredSSP/TLS requirements or older client implementations.

mqtt_check — test a broker's MQTT CONNECT authentication

impacket-mqtt_check 'labreader@mqtt.lab.example' -port 1883 -client-id lab-audit-01
impacket-mqtt_check 'labreader@mqtt.lab.example' -ssl -port 8883 -client-id lab-audit-02

MQTT is a publish/subscribe protocol often used by applications and devices. This script opens a connection to a broker, sends the MQTT CONNECT information, and evaluates the response. The first command uses a normal plaintext port; the second explicitly enables TLS and selects the common TLS port. -ssl and the destination port should be chosen together for the actual broker configuration.

The client ID identifies the MQTT client session; it is not the username. Reusing an existing client ID can interfere with that client's session, depending on broker behavior, so the examples use dedicated identifiers. A successful CONNECT proves the broker accepted that connection, not that the account may read or publish every topic. Topic authorization is a separate application decision.

Offline files: the acquisition happened before this command

esentutl — inspect an Extensible Storage Engine database

impacket-esentutl ./lab-database.edb info
impacket-esentutl ./lab-database.edb export -table '<TABLE_FROM_CATALOG>'
impacket-esentutl ./lab-database.edb dump -page 10

ESE is a database format used by several Windows components. Impacket's example reads a local database structure: info inspects the catalog, export selects a named table, and dump inspects a page. The table name in the second command must come from the actual catalog; it is not a universal table shared by every ESE database.

This Python utility is not Microsoft's full repair/recovery program with the same familiar name. A database needing transaction-log recovery or using unsupported format details can fail to parse. It does not acquire a locked live database from a remote server. Reading NTDS table structures also does not by itself decrypt directory password material; the database encryption context still matters.

ntfs-read — read a local NTFS volume or volume image

impacket-ntfs-read ./lab-ntfs-volume.img
impacket-ntfs-read ./lab-ntfs-volume.img -extract '\Windows\System32\config\SAM'

This example interprets NTFS structures, including file records and data runs, from a local volume. The first form opens its explorer; the second extracts the selected path from that volume. A raw NTFS volume image is different from a complete partitioned-disk image: the parser must be pointed at the NTFS volume itself, not blindly at an unrelated disk-image header.

Raw-device access may require local privileges, but an already readable image file does not gain anything from sudo. This bypasses the live Windows file-access API because the data is being read as an acquired filesystem image; obtaining that image is a separate privileged step. BitLocker or EFS-protected content is not decrypted merely by parsing NTFS. The tool is read-only toward the source, while extracted files are local output artifacts.

samedit — change a password in an offline SAM hive copy

python3 /usr/share/doc/python3-impacket/examples/samedit.py labuser ./SAM.working-copy -system ./SYSTEM.copy -password '<NEW_LAB_USER_PASSWORD>'

SAMEdit opens a local SAM hive and replaces a selected local account's stored password material. labuser names the account inside the hive, SAM.working-copy is the file being modified, and the matching SYSTEM hive provides the boot-key context. -bootkey can supply that key directly, while -hashes supplies replacement hash material instead of a plaintext password.

This is an in-place edit, which is why the example explicitly uses a working copy. It does not contact a running Windows host, reset a domain account, or bypass BitLocker. The wider security issue is whether an actor can obtain and replace the relevant offline system files. A successful edit of a copied hive is not proof that the live machine's account was changed, and restoring altered system files is a separate, potentially disruptive operation.

Specialized techniques and older vulnerability examples

wmipersist — register a WMI event subscription that can execute a script

WMI can react to events without a user manually starting a program each time. A permanent event subscription has a filter describing when to trigger, a consumer describing what action to perform, and a binding connecting them. This tool creates or removes those objects through DCOM/WMI. It is different from WMIExec's one-shot process creation.

impacket-wmipersist 'lab.example/labadmin@srv01.lab.example' install -name LabMarker -vbs ./lab-marker.vbs -timer 60000
impacket-wmipersist 'lab.example/labadmin@srv01.lab.example' remove -name LabMarker

The first example assumes a prepared harmless VBScript file for the lab, such as one that writes a timestamp into a dedicated test file. -vbs reads that local script and stores its contents in an ActiveScript event consumer; -name names the subscription objects. -timer 60000 creates a timer-based trigger with a 60,000-millisecond interval. This can execute repeatedly, not merely once after the command returns.

Alternatively, -filter supplies a WQL event condition. This implementation requires a filter or a timer, not both. The account needs appropriate rights over the subscription namespace, typically administrative rights. Execution is performed later by the consumer infrastructure in its configured security context; it is not a shell kept alive by the Kali terminal.

The second command removes the objects associated with the same name. Use a dedicated name that does not collide with an existing subscription, and verify the filter, consumer, binding, and timer state afterward. A successfully created consumer without its binding or trigger is not proof that the intended action actually ran.

goldenPac — demonstrate the historical MS14-068 Kerberos PAC flaw

impacket-goldenPac 'lab.example/alice@dc01.lab.example' -dc-ip 192.0.2.10 -w ./ms14-068-lab.ccache None

GoldenPAC targets the historical MS14-068 PAC-validation vulnerability. On a specifically vulnerable DC, forged authorization data could be accepted during the Kerberos exchange, allowing an authenticated low-privilege account to obtain elevated authority. This is a vulnerability-dependent path, not the same prerequisite as Ticketer already possessing the krbtgt key. Microsoft documented the flaw and its update in MS14-068.

The identity supplies a valid lab account, -dc-ip selects the DC, and -w writes the resulting cache when the vulnerable exchange succeeds. The literal positional None tells this script not to run its PsExec stage. Without that selection, the tool can continue into remote execution; it is not merely a ticket-inspection utility.

A patched DC should not be treated as vulnerable merely because Kerberos is reachable or normal users can request tickets. The correct learning point is which authorization data the vulnerable KDC trusted, and why server-side verification changed that outcome. A failed run on a modern domain is not evidence that ordinary Kerberos authentication is broken.

raiseChild — show the impact of a compromised child domain within a forest

impacket-raiseChild 'child.lab.example/childadmin' -w ./forest-lab.ccache

This is a compound automation tool. It assumes substantial control in a child domain, including the ability to obtain required child-domain secrets. It discovers parent/forest information, obtains key material, constructs a ticket carrying additional authorization claims, and attempts access to forest-root credential material through the intra-forest trust relationship. It does not turn an ordinary child-domain user into a forest administrator from nothing.

-w saves the generated cache; it does not restrict the run to saving a file. The normal workflow can still perform privileged credential-replication operations. -targetRID selects the target account RID used by its credential-retrieval stage, and -target-exec adds a PsExec stage against a selected host. Those flags change the effects of the overall chain.

The underlying lesson is that a child domain inside a forest should not be assumed to isolate the forest from a compromised domain administrator. Actual success depends on the trust relationship, SID filtering and other controls, keys, target validation, and available protocols. Do not generalize this intra-forest example to every external trust or treat a locally generated ticket as proof of parent-domain compromise.

sambaPipe — load a shared library through a vulnerable Samba server

impacket-sambaPipe 'labuser@samba.lab.example' -so ./lab-proof.so

This example targets CVE-2017-7494. It uploads a prepared shared library to a suitable writable Samba share, determines the server-side share path, and uses the vulnerable named-pipe/module-loading behavior to have the server load that library. The library must match the server platform and implement the intended benign lab proof; this command does not build it.

-so selects the local shared-library file. SMB credentials are useful when the writable share requires authentication, but the decisive prerequisites also include a vulnerable Samba build and the relevant server configuration. Write access to a share alone does not imply that a patched server will load arbitrary libraries. Loading the library is the execution event; whether it exposes a shell depends on the library's own behavior.

Read the affected and fixed versions in the Samba advisory. This is an old vulnerability-specific technique. It is not the Windows service-manager mechanism used by PsExec, despite both starting from SMB file access.

kintercept — proxy Kerberos TCP traffic for protocol experiments

python3 /usr/share/doc/python3-impacket/examples/kintercept.py 192.0.2.10 --server-port 88 --listen-addr 127.0.0.1 --listen-port 1088

KIntercept listens locally and forwards TCP traffic to the selected upstream server. In this example the listener is on loopback port 1088 and the upstream is the lab KDC on port 88. A separately configured lab client or forwarding arrangement must direct its traffic into that listener; starting the program does not intercept the network automatically.

The script contains request/reply handlers for historical Kerberos experiments. --request-handler can select its s4u2else:USER handler, while --reply-handler selects a supported reply transformation. The relevant examples explore S4U name/checksum handling associated with CVE-2018-16860 and CVE-2019-0734. Changing bytes in a request is not enough to make a patched KDC accept invalid authorization data.

This is an older development example with legacy Python/dependency assumptions. The plain proxy combination above explains transport placement without selecting an identity-changing handler. It is a TCP proxy, not a transparent capture tool for all Kerberos UDP traffic, and it does not provide missing session keys or domain privileges.

Packet examples: understand what is visible on the wire

ping — construct an IPv4 ICMP echo packet

sudo impacket-ping 192.0.2.50 192.0.2.20

This old example takes two positional arguments: source IPv4 address and destination IPv4 address. The source should be an address actually assigned to the lab interface you are using. The script builds the IP/ICMP packet with Impacket, sends it through a raw socket, and decodes matching echo replies. Raw-socket privileges explain sudo here; it does not grant rights on the remote host.

It repeats until interrupted and does not accept the full option set of the system ping utility. An echo reply demonstrates an ICMP path and a responding host. Silence can mean filtering, routing trouble, or a host that does not answer ICMP, so it is not sufficient proof that SMB, LDAP, or Kerberos is unavailable.

ping6 — construct an IPv6 ICMP echo request

sudo impacket-ping6 2001:db8:1::50 2001:db8:1::20

The two arguments are source and destination IPv6 addresses in the imaginary lab. This script builds ICMPv6 echo requests and decodes replies through a raw IPv6 socket. Use a source address assigned to the interface and a routable destination for the lab; these documentation addresses are placeholders.

Like its IPv4 counterpart, it runs a loop until interrupted and is primarily a packet-construction example. IPv4 and IPv6 paths can have different firewall rules and routes, so success on one does not establish success on the other. Link-local addresses also require correct interface scoping; do not assume every feature of the operating system's ping6 client exists here.

sniff — capture visible packets with libpcap and a BPF filter

sudo impacket-sniff 'tcp port 445 and host 192.0.2.20'

This example uses pcapy/libpcap. It lists/selects an available interface and treats the supplied arguments as a BPF capture filter. The filter here limits processing to TCP port 445 traffic involving the selected lab host. Impacket then decodes packets into human-readable protocol structures.

This is passive capture on the chosen interface, not a request to log in to SMB. It can only inspect traffic visible at that capture point; a switched network does not normally deliver every other host's traffic to Kali. Encrypted payloads remain encrypted without the corresponding secrets and protocol support. The example prints decoded packets; it is not a full replacement for a capture program's file-output and analysis options.

sniffer — decode packets delivered to raw protocol sockets

sudo impacket-sniffer icmp tcp udp

Sniffer is a separate raw-socket example. Its positional values are IP protocol names, not a BPF expression. It opens a socket for each selected protocol and uses Impacket's IP decoder on packets received through those sockets. With no arguments, its default protocol list is ICMP, TCP, and UDP.

The operating system and privileges determine which packets those sockets receive. There is no directory of remote hosts being queried and no authentication step. Use it to understand packet parsing in a lab; it does not reveal encrypted application data or become a network-wide tap simply because the process runs as root.

split — separate an acquired packet capture into endpoint-based files

impacket-split ./lab-session.pcap

Split reads a local pcap file, filters for the supported IPv4 TCP traffic, and writes smaller pcap files named from address/port endpoints. There is no network connection. The input must use a supported link-layer format; it is not a universal pcapng, IPv6, UDP, or application-stream processor.

Run it in a dedicated working directory because the output files are created there. In the reviewed implementation, endpoint ordering can result in separate directional files, so inspect which directions were retained instead of assuming one perfectly merged bidirectional session. Separating packets does not reconstruct a file transfer, decrypt TLS, or recover a password. It simply makes a capture easier to examine in smaller pieces.

Choosing a tool and interpreting its result

Now we can see why “I have credentials, which tool gives a shell?” is incomplete. First identify the account, protocol, and permission. A user allowed to read LDAP can enumerate directory objects. A user allowed to read an SMB share can retrieve files. Creating a service, starting a WMI process, requesting replication secrets, and modifying an AD DACL require different authority. Choose the tool that exercises the specific permission you are trying to understand.

  • A password or hash works, but access is denied: authentication succeeded somewhere, but the requested operation may require another right. Check account context, token filtering, object ACLs, and service policy.
  • PsExec fails before starting a service: separate the share-upload stage from the SCM stage. Writable storage and service-creation rights are independent.
  • WMIExec creates a process but prints nothing: the RPC execution path and SMB output path have different connectivity and access requirements. Avoid repeating a state-changing command until you know which stage failed.
  • Kerberos reports a principal or encryption error: check the realm, target hostname/SPN, selected KDC, usable cache, time, and key type. An IP change does not rewrite every service identity.
  • A roasting tool writes a hash-like string: it obtained offline-verification material. It has not necessarily recovered a password or a reusable NT hash.
  • A relay listener receives authentication: verify whether it authenticated to the intended destination and what operation that identity could perform. A received handshake alone does not demonstrate impact.
  • An offline parser succeeds: the conclusion concerns the acquired file. It does not prove access to the live host or a change to that host.
  • An old exploit example exists in Kali: availability of its source does not mean the target still has the historical vulnerability.

For us as pentesters, the useful result is a clear chain of evidence: this identity reached this interface, the server permitted this operation, and this was the resulting access or change. That explanation is more valuable than a screenshot of a tool banner. Once we understand the protocol and the permission behind a command, both successful results and failures start making sense.
